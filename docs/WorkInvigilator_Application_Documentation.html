01

What is WorkInvigilator?

WorkInvigilator (internally codenamed kd-tracker) is a disclosed workplace monitoring and HR management platform built for remote work-from-home teams. The word "disclosed" is central to its design — employees are always aware they are being monitored, must provide explicit consent before any capture begins, and see a visible tray icon at all times while the desktop agent is running.

The platform was designed for KD Marketing, a company whose remote employees are distributed across multiple time zones. It solves four problems simultaneously: attendance accountability, productivity visibility, payroll accuracy, and HR compliance.

Core Capabilities

⏱ Attendance Tracking

Punch in/out with break management, 9-hour shift targets, idle detection, auto-close for forgotten shifts, and attendance correction requests.

📸 Capture Pipeline

Randomised screenshots of all displays, periodic audio samples (consent-gated), keystroke/mouse counts and active window title — all with a 31-day retention policy.

💰 Payroll

Monthly payroll generation with daily rates, bonuses, paid leave, company holiday pay, idle deduction option, payslip PDF generation and email delivery via Resend.

🏖 Leave Management

Sick, bereavement, personal, emergency, and vacation leave — with half-day support, proof document upload, approval workflow, and payroll integration.

🏢 Department Hierarchy

First-class departments with assigned leaders. Leaders can view their team, approve leave, and monitor live attendance — without admin-level access.

🔒 Security & Consent

JWT auth with rotating refresh tokens, TOTP 2FA, full session management, login history, consent-at-ingest-time for audio, and complete audit logging.

Design Principles

  • Disclosed monitoring: Employees always know. Consent is a hard gate — the server rejects audio unless consent_audio = true at ingest time.
  • Offline-first agent: Network outages do not penalise employees. Punch events and captures queue locally and are delivered with original timestamps when connectivity returns.
  • Portable persistence: SQLite by default, PostgreSQL-ready. No SQLite-specific SQL, no floating-point money, epoch milliseconds everywhere.
  • httpOnly cookies only: The web portal never exposes tokens to browser JavaScript. All API calls go through a BFF proxy that injects tokens server-side.
  • Idempotent operations: Payroll regeneration overwrites via unique constraints. Scheduled jobs are safe to re-run.
  • Least privilege: Leaders see only their department. Employees see only themselves. Audit logs record every admin access to monitoring data.

Key Architecture Decisions

DecisionWhatWhy
ADR-0001SQLite-first, Postgres-compatible schemaSmall team can run on a single VPS without a DB server; schema uses no SQLite-specific features, so migration to Postgres requires only a config change
ADR-0004Offline outbox with backdatingEmployees' internet can drop; a network outage must not create an absence. Backdated timestamps accepted up to 4 hours; server rejects beyond that
ADR-0005Multi-display captureEach display is a separate row so a failed upload of one screen does not lose the others

httpOnly cookiesWeb portal never exposes tokensXSS cannot steal tokens if they are never in JS scope; BFF proxy adds the Bearer header server-side

Scheduled Jobs & Cron

Four jobs run automatically via node-cron. Each execution is recorded in the job_runs table. The GET /health/jobs endpoint exposes the last run of each job for external monitoring. If the purge job has not run in 48 hours, the endpoint returns HTTP 503.

JobCron (default)What it doesKey behavior
purge 15 2 * * *
(2:15 AM daily)		 Delete capture files older than RETENTION_DAYS (default 31) Sets file_deleted = true, nulls image_url / file_url. Rows kept permanently for audit. Deletes from both local disk and S3 if configured.
close-shifts 10 * * * *
(every hour :10)		 Auto-close any shift open longer than SHIFT_AUTO_CLOSE_HOURS (default 16 h) Sets status = closed, auto_closed = true, needs_review = true. Calculates worked seconds at close time. Does not touch breaks in progress.
payroll 0 3 1 * *
(3 AM on 1st of month)		 Generate payroll summaries for the previous month for all active employees Idempotent: regenerates if already present. Applies daily rates, leave days, holiday pay. Does not finalize — HR must do that manually.
birthdays 5 8-20 * * *
(every hour 8am–8pm)		 Send birthday notifications for employees whose birthday is today (company timezone) Writes one notification per birthday per day (idempotent — safe to repeat). Only active employees.

Authentication Flow

Web Portal Login Flow

  1. Employee submits email + password at /login
    Browser POSTs to /bff/login (Next.js route handler, not the BFF proxy). Rate limited: 5 attempts per 15 minutes.
  2. BFF login handler calls backend POST /api/auth/login
    If 2FA is not enabled, backend returns { accessToken, refreshToken, expiresIn, employee }. If 2FA is enabled, returns { challengeToken } instead.
  3. [2FA only] Employee enters TOTP code at /login/2fa
    Browser POSTs { challengeToken, code } to /bff/api/auth/2fa/verify. After 5 wrong codes in 15 minutes, the account is temporarily locked.
  4. BFF writes three httpOnly cookies
    kd_access = access token · kd_refresh = refresh token · kd_expiry = expiry epoch ms. All cookies are httpOnly, SameSite=Lax. JS cannot read them.
  5. Middleware transparently refreshes the token when needed
    On every request, middleware checks kd_expiry. If the token expires within 60 seconds, it POSTs to /api/auth/refresh, updates all three cookies, and patches the in-flight request so the page sees the new token — zero user action required.
  6. All API calls go through the BFF proxy
    Browser calls /bff/api/.... The BFF route handler reads the access token from the httpOnly cookie and adds Authorization: Bearer <token> before forwarding to the backend. Tokens are never in browser memory.

Desktop Agent Login Flow (Connect Code)

  1. Employee signs into the web portal (steps 1–4 above)
    The web portal shows a "Connect desktop agent" button on the /download page.
  2. Portal calls POST /api/auth/agent-code
    Backend generates a random code, stores its SHA-256 hash in agent_connect_codes, returns the plain code. Single-use, expires in ~5 minutes.
  3. Portal opens workbuddy://connect?code=... deep link
    The Electron app registers the workbuddy:// URI scheme. This deep link launches/focuses the agent and passes the code.
  4. Agent calls POST /api/auth/agent-token with the code
    Backend verifies the hash, marks the code used, issues a fresh agent-scoped token pair for that employee. The agent stores tokens in its encrypted local token store.
  5. Agent uses Bearer tokens for all subsequent calls
    The ApiClient auto-refreshes the access token on 401. If a 401 persists after refresh (account deactivated or password reset), agent.markSignedOut() is called — the tray icon prompts re-login.
TOKEN LIFECYCLE: Access Token → 30 min TTL → refreshed by middleware (web) or ApiClient (agent) Refresh Token → 14 day TTL → rotated on every use → old token valid for 120s grace window (covers lost responses in transit) SECURITY NOTES: • Wrong password: rate limited (5 / 15 min) • Account inactive: login returns 401 'deactivated' • Token stolen + used: rotation means old token is immediately invalid • 401 after refresh: session revoked → agent/portal prompts re-login • Admin can revoke any session via /api/auth/sessions/:id

Two-Factor Authentication (TOTP)

Setup Flow

  1. Employee visits /security → clicks "Set up two-step sign-in"
    Calls POST /api/auth/2fa/setup. Backend generates a TOTP secret (encrypted before storing in employees.totp_secret), returns a QR code URI for the authenticator app.
  2. Employee scans QR code with an authenticator app (Google Authenticator, Authy, etc.)
  3. Employee enters the 6-digit code
    Calls POST /api/auth/2fa/enable with the code. Backend verifies using the secret, records totp_enabled_at, and generates 10 one-time recovery codes (hashed, stored in recovery_codes). Recovery codes are shown once — employee must save them.

Login with 2FA

  1. POST /api/auth/login — backend sees totp_enabled_at is set
    Returns { challengeToken } instead of tokens. The challenge token is a short-lived JWT containing the employee ID.
  2. POST /api/auth/2fa/verify with challengeToken + code (or recoveryCode)
    Backend verifies the code against the TOTP secret. totp_last_step is updated to prevent code replay. After 5 wrong codes in 15 minutes → account held, further attempts rejected.
  3. Backend issues full token pair on success
    Session is created with second_factor = true.
Admin enforcement: Settings can require all admin accounts to have 2FA enabled (require_admin_2fa = true). An admin without 2FA is redirected to set it up on their next login.

Consent System

Consent is a hard gate — no capture happens without it. The consent disclosure text is served from the backend (GET /api/auth/consent) so it cannot drift between client versions.

FieldWhat it gates

Consent Enforcement Points

  • Web portal: New employees are redirected to /consent before they can punch in. Without consent_monitoring, the punch-in call is blocked.

Attendance — Punch In / Out / Break Workflow

Shift State Machine

[punched_out] │ │ POST /api/attendance/punch-in │ (blocked on Sundays + holidays if enforceDayOff=true) │ (blocked if another open shift exists for this employee) ▼ [working] ◀──────────────────────────────────────────────┐ │ │ │ POST /api/attendance/break-start │ POST /api/attendance/break-end ▼ │ [on_break] ───────────────────────────────────────────────┘ │ │ POST /api/attendance/punch-out │ OR auto-close (cron, after 16+ hours) │ OR logout (puts on break instead of closing) ▼ [closed] CONSTRAINTS: • One open shift per employee (DB unique partial index) • Backdating: agent can submit timestamps up to 4 hours in the past (offline resilience) • Clock skew: timestamps more than 2 minutes in the future are rejected • Break allowance: 1 hour total per shift (configurable). Exceeding it sets over_break=true • Idle detection: no input for 10+ min → idle_seconds accumulates

Punch-In Flow (Detailed)

  1. Employee clicks "Punch In" (web portal) or presses the button in the desktop agent
  2. POST /api/attendance/punch-in
    Backend checks: employee active? consent_monitoring true? no existing open shift? not a holiday/Sunday (if enforceDayOff)? If all pass, creates attendance row with status=open.
  3. Response includes captureAllowed and audioAllowed
    Desktop agent immediately starts screenshot capture and (if audioAllowed) arms the audio scheduler. First screenshot is taken immediately, not after the first random interval.
  4. Agent polls GET /api/attendance/status every tick
    Response includes current state, worked seconds, break remaining seconds, captureAllowed. Agent updates tray icon and tooltip to reflect live state.

Offline Resilience & Outbox Queue

Design goal: An employee's broadband going down for a few hours should not create gaps in attendance records or capture uploads.
OUTBOX QUEUE (desktop-agent/src/core/outbox.js) │ Local SQLite database on the agent machine │ ├─ Accepts any enqueued item immediately (never blocks) │ Item types: punch | screenshot | audio | activity │ ├─ When network is available: │ uploader.drain() → processes queue in order: │ │ │ ├─ POST item to backend endpoint │ │ • punch events include the original `at` timestamp │ │ • captures include their `capturedAt` / `recordedAt` │ │ │ ├─ Success (2xx): remove item from queue │ ├─ 4xx (bad request): mark item abandoned (do not retry indefinitely) │ └─ Network error / 5xx: leave in queue, retry after backoff │ └─ agent.refreshQueueStats() called after each drain pass → updates tray icon's "pending: N" display BACKEND CONTRACT (ADR-0004): • punch-in with at= up to MAX_BACKDATE_HOURS (4h) in the past → accepted as backdated • captures with capturedAt up to MAX_CAPTURE_AGE_DAYS (7d) in the past → accepted • timestamps more than MAX_CLOCK_SKEW_SECONDS (120s) in the future → rejected (clock error) OPTIMISTIC STATE (agent while offline): When a punch event is queued (network down): • Agent immediately shows the optimistic state (working / on_break / punched_out) • Capture starts or stops based on the optimistic state • Break deadline estimated from last server figure: allowance − already-used seconds • When network returns: syncStatus() corrects state from server

BFF Proxy Architecture

The Backend For Frontend (BFF) pattern keeps access tokens out of browser JavaScript entirely. The BFF is a Next.js Route Handler at /app/bff/[...path]/route.js that acts as an authenticated reverse proxy.

ConcernHow it's handled
Token storageThree httpOnly cookies: kd_access, kd_refresh, kd_expiry. Browser JS has zero access.
Token injectionBFF reads kd_access from Next.js cookies() store (server-side), adds Authorization: Bearer header.
Token refreshMiddleware runs before every request (pages and BFF calls). Refreshes transparently if token expires within 60s.
CSRF protectionCookies are SameSite=Lax. BFF additionally checks Origin header on all mutating requests — must match the portal's own origin.
Path restrictionBFF only forwards /api/* paths. Any other path returns 404. Cannot be used as an open proxy.
Audio seekingRange header forwarded through; content-range and accept-ranges headers returned. Enables HTML audio seek without re-downloading.
Content-length accuracyBody buffered in full; content-length set from actual bytes. Avoids CDN compression length mismatch (compressed header + decoded body = wrong length).

Departments & Leaders

How Departments Work

  • Departments are first-class entities in the departments table (id, name, description).
  • Each employee has a department VARCHAR column that stores the department name, kept in sync when HR assigns an employee to a department.
  • The leader role is assigned to individual employees. A leader can be assigned to one or more departments.
  • The department_leaders junction links leader employee IDs to department names.
  • All /api/leader/* queries filter by the calling leader's department memberships — a leader cannot see data from other departments.

Admin Workflow for Departments

  1. Create a department at /admin/departments
    POST /api/admin/departments { name, description }
  2. Assign employees to the department
    PATCH /api/admin/employees/:id { department: "Sales" }
  3. Assign a leader role to an employee
    PATCH /api/admin/employees/:id { role: "leader", leaderDepartments: ["Sales"] }
  4. Leader signs in → sees /leader with their departments
    Leader's department list, member live counts, and leave queue are scoped to their departments.

Projects fill the "what work drove the hours" gap. Within a shift, an employee can switch between projects, and each segment of time is recorded with a start and nullable end time — the same pattern as breaks.

Branding & Company Calendar

Branding

  • The PUBLIC_API_URL env var provides the publicly reachable URL for email clients to fetch the logo image

Company Calendar (Holidays)

  • Admins manage company holidays at /admin/settings → Calendar tab
  • Each holiday: date (YYYY-MM-DD, unique), name, created_by
  • Holidays affect three features:
    1. Attendance: Punch-ins blocked on holidays (if ENFORCE_DAY_OFF=true)
    2. Payroll: Holidays on working days → holiday_days count → paid at daily rate
    3. Leave: Leave spanning holidays only consumes working days (not the holiday itself)
  • Employees view the calendar at /me/calendar and /calendar

Data Retention & Purge Policy

Retention applies to files only. Database rows are never deleted by the purge job. Only the binary files (screenshot images, audio recordings) are removed after RETENTION_DAYS (default 31 days).

Purge Mechanics

Backend First-Start Checklist

  1. Set all required environment variables
    JWT_SECRET, JWT_REFRESH_SECRET (32+ chars each), DB config, STORAGE config, CORS_ORIGINS pointing to your web portal URL.
  2. Run database migrations
    node src/db/cli.js migrate:latest — creates all tables from migration files in order.
  3. Create the first admin account
    node src/db/createAdmin.js — creates an admin employee with the email and password you provide.
  4. Start the server
    node index.js or pm2 start index.js --name workinvigilator-api
  5. Verify health
    GET /health — should return { status: "ok", database: "sqlite", ... }

  1. Set environment variables
    API_BASE_URL = your backend URL. BFF_KEY = shared secret. NEXTAUTH_SECRET or equivalent session secret if used.
  2. Build and deploy
    npm run build then npm start (or deploy to Vercel via git push).
  3. Test login
    Log in with the admin account created above. Navigate to /admin — should show the live board.

Production Security Checklist

  • ✅ JWT_SECRET and JWT_REFRESH_SECRET are 32+ chars and do not contain "dev-only"
  • ✅ BANK_DATA_KEY is set (required for bank details encryption)
  • ✅ CORS_ORIGINS is set to only your web portal's domain(s)
  • ✅ DB is not SQLite for multi-instance deployments (or use a shared SQLite volume)
  • ✅ STORAGE_DRIVER=s3 with a private bucket (not public)
  • ✅ RESEND_API_KEY and MAIL_FROM set for payslip emails
  • ✅ ENFORCE_DAY_OFF=true (default in production)
  • ✅ HTTPS everywhere — backend behind nginx/ALB with TLS
  • ✅ Trust proxy set (app.set('trust proxy', 1)) — already done for IP accuracy behind load balancers
  • ✅ Consider requiring admin 2FA (settings.require_admin_2fa = true)
