01

Recommendation

Go

Backend and web portal can go to production now. This audit pass read every backend module, every web request-handling path, and the desktop agent's core logic specifically hunting for concurrency bugs and silent data loss — the class of defect that unit tests written in isolation don't naturally surface. Ten were found; all ten are fixed, tested, and three were confirmed against the live server with real concurrent HTTP requests, not just simulated in one process.

Do not distribute a desktop agent installer built on a machine that skipped the native-module rebuild step (§05) — it will crash on launch, silently, with no error a user could report.

02

Bugs found & fixed

Ordered by category. The largest group — four of ten — is the same shape of bug in four different places: a "check, then write" sequence that isn't atomic, so two requests landing close together can both pass the check.

01 Race condition attendance.service.js · punchIn() Live-verified
Two punch-ins could both succeed for one employee
A double-click, a client retry, or the desktop agent and the web portal both firing at once could each pass the "no open shift exists" check before either wrote a row — SQLite's transaction takes no write lock until the INSERT itself. Result: two open shifts for the same employee, corrupting the day's attendance record.
Fix

Added a database-level partial unique index — attendance(employee_id) WHERE status IN ('open','on_break') — a real constraint, not an application-level hope. Verified with 5 concurrent real HTTP punch-ins against the running server: exactly one 201, four clean 409s, one row in the database.

02 Race condition closeShifts.job.js · the hourly sweep
The stale-shift sweep could overwrite a real punch-out
The sweep reads a batch of stale shifts, then runs several more queries per shift before its own write. If an employee genuinely punched out for real inside that window, the sweep's unconditional write silently replaced their real punch-out with its own estimate — flagging a normal day as "never punched out" and recording the wrong hours.
Fix

Re-reads each shift immediately before acting, and guards the final write with WHERE status IN ('open','on_break') — a real punch-out that already closed it makes the guarded write match zero rows instead of clobbering it.

03 Race condition admin.service.js · createEmployee()
A duplicate work email could crash with a raw 500
Same check-then-insert shape: two admins (or one double-click) creating the same email at once could both pass the pre-check, and the loser hit an unhandled database error instead of the intended "already exists" response.
Fix

Catches the database's unique-constraint violation and returns the same clean 409 the non-racing path already gives.

04 Race condition payroll.service.js · generate() Live-verified
Two simultaneous payroll runs for one month could 500
The same pattern again on the per-employee upsert: two POST /payroll/generate calls for the same month racing on their own check-then-write could fail the loser instead of the idempotent overwrite the endpoint promises.
Fix

Catches the violation and falls back to the update the winner's insert should have raced against.

05 Data loss jobRunner.js
Partial job failures lost the detail that made them actionable
A retention purge that fails partway through attaches exactly which files succeeded and which didn't — the generic error handler kept only the top-level message, discarding it. An operator looking at a failed run had no way to tell which files failed without reading raw server logs from the moment it happened.
Fix

Both fields are now preserved on the stored job-run row, and the partial success count surfaces directly on it.

06 Data loss payroll.service.js · markSynced()
An empty employee list was silently treated as "everyone"
employeeIds?.length is falsy for both undefined and [] — an explicit empty array, meant as "these zero employees," fell through to "mark the whole month synced" instead.
Fix

Distinguishes "omitted" from "explicitly empty" with an Array.isArray check before deciding the scope.

07 Session handling web/lib/api.js
A deactivated employee hit a crash page, not a sign-in prompt
Deactivation arrives as 403 ACCOUNT_DEACTIVATED, not 401 — the access token itself hasn't expired, so the middleware's time-based refresh check never notices. The old code only redirected on 401, so this landed on the generic error boundary instead.
Fix

Redirects to sign-in on either 401 or the ACCOUNT_DEACTIVATED code.

08 Session handling web/lib/client.js
Same gap, on every button click instead of every page load
Punch and admin actions taken after deactivation showed an inline error banner and left the employee stuck on a dead page rather than returning them to sign-in.
Fix

The same check, centralised in the one function every browser-side action already goes through.

09 Session handling web/middleware.js
Token refresh assumed a lifetime instead of reading it
The in-flight cookie rewrite during a refresh hardcoded 30 minutes rather than using the value the API actually returned — harmless only because nothing downstream reads it within that same request, but it would have silently drifted from reality the moment the token lifetime setting was ever changed.
Fix

Computed from the real expiresIn the refresh response returns, with the same formula the persisted cookie already used.

10 Interface globals.css · popup.html Live-verified
Light theme, by request
Both the web portal and the desktop agent's tray popup auto-switched between light and dark based on the OS preference.
Fix

Converted to light-only on both surfaces. Verified in-browser with the OS forced to dark mode — the portal still renders light.

04

Security posture

What's already in place, and what to check before a public-internet deployment — this was built assuming an internal or VPN-reachable API.

✓

Bcrypt password hashing; login gives an identical response and timing shape for an unknown email and a wrong password — no account-enumeration oracle.

✓

Session tokens live in httpOnly cookies behind a server-side proxy — never in localStorage, never readable by page JavaScript.

✓

Refresh-token rotation with a short grace window for legitimate retries; reuse outside the window revokes every session on the account — now correctly triggered for the deactivated-account case too.

✓

Role checks run server-side against the current database row on every request, never trusted from a token claim — a role or status change takes effect on the very next request.

✓

CSV exports are guarded against formula injection; uploads are rate-limited; every admin view of a screenshot or audio file writes an append-only audit row.

✓

Consent is enforced server-side: no audio upload is accepted without consent_audio = true on the employee row, re-checked on every request.

05

Packaging blocker

The one open item. The agent's logic is done and live-verified; producing an installer is not.

!

better-sqlite3 crashes inside Electron on Windows

The bundled Windows binary crashes the whole Electron process — uncatchable, no JS error at all — the instant it opens a database. Confirmed against both Electron 33 and Electron 30 on the build machine. The fix is standard for native Node modules under Electron: rebuild the module against Electron's own headers, which needs a C++ toolchain. By explicit customer decision this toolchain was not installed — deferred to whichever machine actually produces the packaged build.

Windows
Visual Studio Build Tools — "Desktop development with C++" (not the IDE, not an editor) · npm run rebuild:native
macOS
xcode-select --install · npm run rebuild:native
Linux
build-essential (or distro equivalent) · npm run rebuild:native

Deploy checklist

NODE_ENV=production on the API — it already refuses to start with default JWT secrets, by design

JWT_SECRET / JWT_REFRESH_SECRET set to strong, generated values (32+ characters)

CORS_ORIGINS set to the real portal origin only

STORAGE_DRIVER=s3 with bucket credentials, if running more than one API instance

TLS in front of both the API and the portal; COOKIE_SECURE=1 on the portal

/health/jobs wired into an external monitor — it returns 503 if the retention purge hasn't succeeded in 48 hours

Seed/demo data not run against production — db:seed already refuses to run with NODE_ENV=production

Desktop agent: no installer distributed from a machine that couldn't run npm run rebuild:native successfully
